# 京东新品明星红包自动化设计

## 目标

从 Charles 抓包 `jd_新品明星红包.chls` 还原新品明星红包活动中可获取京豆、红包或超市卡的完整流程，并在项目中新增独立脚本 `jd_xinpin_mingxing_hongbao.js`。旧脚本 `jd_xinpin_hongbao_bean.js` 不做修改。

最终脚本只保留一种可运行实现。优先交付纯 Node.js 实现；仅当 Node.js 因浏览器运行态签名或风控上下文无法工作时，才在调试阶段使用 Headless Chrome 定位差异，并在最终代码中删除未采用的路线。

## 输入与产物

输入文件：

- `/Users/lifeng/test_data/charles/jd_新品明星红包.chls`

输出文件：

- `files/jd_新品明星红包.har`：通过 Charles 软件无界面转换得到的完整 HAR。
- `files/jd_新品明星红包_filtered.har`：用于分析的精简 HAR。
- `jd_xinpin_mingxing_hongbao.js`：新品明星红包自动化脚本。
- 自动化测试文件：覆盖 HAR 筛选、业务任务识别和日志脱敏等确定性逻辑。

## HAR 转换与筛选

使用已安装的 Charles 可执行文件进行格式转换，不使用第三方解析器代替 Charles 读取 `.chls`。转换完成后验证 HAR 能被 JSON 解析，且包含标准的 `log.entries` 数组。

筛选时保留原始 HAR 顶层结构和请求时序，只过滤 `log.entries`：

1. 保留主机名为 `jd.com` 或以 `.jd.com` 结尾的全部请求。
2. 对主机名为 `360buyimg.com` 或以 `.360buyimg.com` 结尾的请求，仅保留可判定为 JavaScript 的资源。
3. JavaScript 判定依次参考 URL 路径扩展名、响应 `content.mimeType`、响应 `Content-Type`。URL 查询参数不参与扩展名判断。
4. 其他域名请求全部移除。
5. 保留匹配 entry 的请求、响应、时间、Cookie 等原始 HAR 字段，以便离线复盘；HAR 文件本身不写入运行日志。

筛选实现采用结构化 JSON 解析，不使用文本替换。输出后再次解析并检查每条 entry 都满足筛选条件。

## 流程分析

按 HAR 的 `startedDateTime` 排序并结合页面 JavaScript 分析接口调用关系，重点识别：

- 活动初始化、活动 ID、页面 ID、楼层 ID 及活动状态查询；
- 任务列表、任务类型、任务状态与奖励类型；
- 任务开始、浏览/停留、任务完成、奖励领取；
- 京豆、红包、超市卡对应的奖励字段、成功状态和重复领取状态；
- 请求签名、必要 Cookie、设备标识、请求头和 Referer；
- 接口之间需要传递的动态标识，如任务 ID、加密任务 ID、item ID、workflow ID 或 token。

只有 HAR 或页面 JavaScript 能证明的请求才进入脚本。分析阶段不假设旧新品红包活动的 ID、楼层、workflow 或请求体仍然有效。

## 脚本结构与数据流

脚本沿用项目 CommonJS 风格并从 `jdCookie.js` 读取账号。主要职责拆分为短小函数：

- 配置和常量：活动入口、接口标识、超时和日志开关。
- 请求构造：生成 URL、请求头、签名参数和请求体。
- 脱敏日志：打印重要请求与响应，同时隐藏凭据。
- 响应解析：统一处理 HTTP 错误、非 JSON 响应和业务错误码。
- 任务识别：从活动响应中筛选能获得京豆、红包或超市卡的待完成任务。
- 流程执行：按抓包证明的顺序执行查询、开始、浏览、完成和领取。
- 账号调度：账号间串行执行，单账号失败不影响后续账号。

优先复用 `function/jdHarBeanCommon.js` 中已存在且与新抓包协议一致的 Cookie、User-Agent、签名和通用工具。若现有帮助函数不符合新协议，只新增本活动所需的最小实现，不修改无关脚本。

## 重要请求日志

重要接口默认输出以下信息：

- 接口名称和脱敏 URL；
- 请求方法；
- 脱敏后的请求头摘要；
- 脱敏后的请求体；
- HTTP 状态码；
- 业务响应正文；
- 请求耗时和业务结果摘要。

以下内容必须脱敏：

- `Cookie`、`Set-Cookie` 和账号标识；
- `h5st`、`x-api-eid-token`、`eid`、`token`、`authorization` 等签名或令牌；
- URL 查询参数和 JSON/form 字段中的同类敏感值。

脱敏保留字段是否存在、原始长度以及有限首尾字符，便于比较请求差异但不能直接复用凭据。异常日志包含接口名和错误上下文，不吞掉异常。

## Node.js 与 Headless Chrome 决策

开发首先实现 Node.js 请求链并使用真实账号验证。若失败，按照请求构造、签名、Cookie/风控上下文、业务响应四个边界记录证据，确认根因后再决定是否使用 Headless Chrome 进行临时诊断。

只有在抓包证明核心接口依赖无法由项目现有能力复现的浏览器运行态时，最终实现才切换为 Headless Chrome。无论选择哪条路线，交付前必须删除另一条路线的生产代码、配置开关和临时调试文件，保证最终脚本不存在双实现或运行时回退。

## 错误处理

- 网络请求设置明确超时，并报告 HTTP 状态与响应片段。
- JSON 解析失败时保留脱敏后的原始响应用于定位。
- 业务错误码不得当作成功处理。
- 已完成、已领取、活动结束等幂等状态单独识别，不重复执行破坏性操作。
- 单个任务失败时记录上下文并继续安全的后续任务；账号级初始化或签名失败时停止该账号。
- 不在未知状态下猜测领取接口或批量重试奖励请求。

## 测试与验收

自动测试至少验证：

1. HAR 域名和 JavaScript 资源筛选规则。
2. URL 查询参数不干扰 `.js` 扩展名识别。
3. 奖励类型与待处理任务识别。
4. 请求头、URL、JSON 和 form 请求体中的敏感字段脱敏。
5. 非 JSON、HTTP 错误和业务失败响应的处理。

实现遵循测试先行：先观察测试因缺少行为而失败，再编写最小实现使其通过。最终执行语法检查、目标测试、项目相关静态检查，并用真实账号运行脚本。验收标准为：

- 两份 HAR 文件存在且结构合法；
- filtered HAR 中没有违反筛选规则的 entry；
- 能从日志明确看到奖励流程的每个重要请求和响应；
- 真实运行能正确识别并执行抓包中存在的可领奖流程，或准确报告没有待完成/待领取任务；
- 最终脚本只包含一种运行实现。
